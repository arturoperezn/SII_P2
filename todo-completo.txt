FASE 1: DISEÑO DE LA BASE DE DATOS RELACIONAL (schema.sql)
================================================================================
Objetivo: Definir la estructura DDL completa en PostgreSQL que soporte videoclub,
usuarios, catálogo, compras y valoraciones.

[ ] 1.1. Tabla 'usuarios':
    - id (SERIAL PRIMARY KEY)
    - username (VARCHAR UNIQUE NOT NULL)
    - password_hash (VARCHAR NOT NULL)
    - pais (VARCHAR NOT NULL) -- Requerido para el endpoint /ventas/<año>/<país>
    - saldo (NUMERIC(10, 2) NOT NULL DEFAULT 0.0 CHECK (saldo >= 0))
    - created_at (TIMESTAMP DEFAULT CURRENT_TIMESTAMP)

[ ] 1.2. Tabla 'peliculas':
    - id (SERIAL PRIMARY KEY)
    - titulo (VARCHAR NOT NULL)
    - anio (INT NOT NULL)
    - genero (VARCHAR)
    - director (VARCHAR NOT NULL) -- O tabla separada de directores
    - precio (NUMERIC(10, 2) NOT NULL CHECK (precio >= 0))
    - stock (INT NOT NULL DEFAULT 0 CHECK (stock >= 0))
    - created_at (TIMESTAMP DEFAULT CURRENT_TIMESTAMP)

[ ] 1.3. Tabla 'actores' y relación 'pelicula_actores':
    - Para cumplir con el requisito de "gestionar películas, actores y directores".

[ ] 1.4. Tablas para Carrito y Pedidos:
    - Tabla 'pedidos' / 'carritos':
      * id (SERIAL PRIMARY KEY)
      * usuario_id (INT REFERENCES usuarios(id) ON DELETE CASCADE)
      * estado (VARCHAR CHECK (estado IN ('carrito', 'pagado', 'cancelado')) DEFAULT 'carrito')
      * importe_total (NUMERIC(10, 2) NOT NULL DEFAULT 0.0)
      * fecha_creacion (TIMESTAMP DEFAULT CURRENT_TIMESTAMP)
      * fecha_pago (TIMESTAMP NULL) -- Se establece al pagar
    - Tabla 'pedido_items' / 'lineas_carrito':
      * id (SERIAL PRIMARY KEY)
      * pedido_id (INT REFERENCES pedidos(id) ON DELETE CASCADE)
      * pelicula_id (INT REFERENCES peliculas(id) ON DELETE RESTRICT)
      * cantidad (INT NOT NULL DEFAULT 1 CHECK (cantidad > 0))
      * precio_unitario (NUMERIC(10, 2) NOT NULL)
      * UNIQUE (pedido_id, pelicula_id)

[ ] 1.5. Tabla 'valoraciones':
    - id (SERIAL PRIMARY KEY)
    - usuario_id (INT REFERENCES usuarios(id) ON DELETE CASCADE)
    - pelicula_id (INT REFERENCES peliculas(id) ON DELETE CASCADE)
    - puntuacion (INT NOT NULL CHECK (puntuacion >= 0 AND puntuacion <= 10))
    - fecha (TIMESTAMP DEFAULT CURRENT_TIMESTAMP)
    - UNIQUE (usuario_id, pelicula_id) -- Un voto por usuario y película

FASE 2: TRIGGERS Y PROCEDIMIENTOS ALMACENADOS EN POSTGRESQL (schema.sql)
================================================================================
Objetivo: Trasladar la lógica crítica a la base de datos como exige el enunciado
(vale 1.5 puntos de la rúbrica).

[ ] 2.1. Trigger de Stock y Total de Carrito:
    - Nombre sugerido: trg_actualizar_carrito_y_stock
    - Función PL/pgSQL: fn_actualizar_carrito_y_stock()
    - Al insertar un item en 'pedido_items':
      * Verificar si hay stock suficiente en 'peliculas'. Si no hay stock, lanzar excepción (RAISE EXCEPTION).
      * Restar la cantidad del stock disponible en 'peliculas'.
      * Recalcular y actualizar el 'importe_total' en la tabla 'pedidos'.
    - Al eliminar un item de 'pedido_items':
      * Devolver el stock a 'peliculas'.
      * Restar del 'importe_total' en la tabla 'pedidos'.

[ ] 2.2. Trigger de Pago y Deducción Automática de Saldo:
    - Nombre sugerido: trg_pagar_pedido_saldo
    - Función PL/pgSQL: fn_pagar_pedido_saldo()
    - Disparador: BEFORE UPDATE OF estado ON pedidos (cuando pasa de 'carrito' a 'pagado'):
      * Comprobar que el usuario tenga saldo suficiente (usuarios.saldo >= pedidos.importe_total).
      * Si no tiene saldo: lanzar RAISE EXCEPTION 'Saldo insuficiente'.
      * Si tiene saldo:
        - Restar el importe del saldo del usuario (UPDATE usuarios SET saldo = saldo - NEW.importe_total).
        - Asignar NEW.fecha_pago = CURRENT_TIMESTAMP automáticamente.

[ ] 2.3. Procedimiento Almacenado / Función para Valoración Media:
    - Nombre sugerido: sp_calcular_valoracion_media(p_pelicula_id INT)
    - Tipo: FUNCTION o PROCEDURE en PL/pgSQL que devuelva NUMERIC.
    - Calcula el promedio de las puntuaciones de la película en la tabla 'valoraciones' (o 0 si no hay votos).

FASE 4: MICROSERVICIO DE GESTIÓN DE USUARIOS (src/user.py)
================================================================================
Objetivo: Implementar la API de usuarios asíncrona con Quart + SQLAlchemy Core.
ELIMINAR TODO EL CÓDIGO DE FICHEROS JSON DE LA P1.

[ ] 4.1. Configuración de conexión asíncrona:
    - engine = create_async_engine(DATABASE_URL, echo=False)
    - async_sessionmaker para sesiones o uso directo de async with engine.begin() / connect().

[ ] 4.2. Helper de autenticación JWT stateless:
    - Generar token JWT con payload: {"sub": username, "uid": user_id, "exp": ...} firmado con clave secreta.
    - Decorador o función 'require_auth' que lea 'Authorization: Bearer <token>', valide la firma sin consultar la BD, y extraiga el usuario.

[ ] 4.3. Endpoints requeridos:
    - [PUT o POST /user]: Crear usuario (username, password, pais, saldo inicial opcional).
      * Valida datos -> Hashea password con bcrypt -> INSERT con text() parametrizado.
      * Error 400 si faltan datos, 409 si el usuario ya existe.
    - [POST /user/login]: Login.
      * Valida username y password contra el hash en BD.
      * Devuelve token JWT (código 200). Error 401 si credenciales incorrectas, 404 si no existe.
    - [POST /user/logout]: Logout.
      * Como es stateless, devuelve 200 confirmando fin de sesión.
    - [DELETE /user]: Borrar usuario autenticado.
      * Requiere Bearer token.
      * Elimina el usuario de la BD en un único execute().
    - [PATCH o PUT /user/saldo]: Recargar / actualizar saldo.
      * Requiere Bearer token.
      * Recibe cantidad a añadir -> UPDATE con text() parametrizado. Devuelve nuevo saldo.

FASE 5: MICROSERVICIO DE LA API PRINCIPAL (src/api.py)
================================================================================
Objetivo: Implementar el videoclub con Quart + SQLAlchemy Core. Todas las consultas
deben ser prepared statements con text(), execute() y en un ÚNICO execute() por endpoint.

[ ] 5.1. Conexión asíncrona y autenticación:
    - Conectar a la misma base de datos usando SQLAlchemy Core asíncrono.
    - Validar Bearer token para operaciones que requieran sesión activa.

[ ] 5.2. Gestión de recursos principales (Películas):
    - [POST /peliculas]: Crear película (título, año, director, precio, stock).
    - [DELETE /peliculas/<id>]: Borrar película.
    - [GET /peliculas]: Listar películas con filtros (query params: genero, anio, director, titulo).
      * IMPORTANTE: Todo el filtro y proyección en un único execute().

[ ] 5.3. Funcionalidades de consumo (Carrito de compra):
    - [POST /carrito/item]: Añadir película al carrito del usuario actual.
      * Si no tiene carrito activo ('carrito'), se crea uno.
      * Se inserta el item -> El TRIGGER de la BD se encarga de reducir stock y sumar importe.
      * Si el trigger lanza error de stock, devolver HTTP 400/409 con mensaje claro.
    - [GET /carrito]: Consultar el carrito activo del usuario con sus líneas e importe total.
    - [POST /carrito/pagar]: Pagar el carrito actual.
      * Hace UPDATE pedidos SET estado = 'pagado' WHERE id = :pedido_id.
      * El TRIGGER de la BD comprueba saldo, descuenta saldo y añade fecha_pago.
      * Si saldo insuficiente, el trigger falla -> capturar excepción y devolver HTTP 400 (Saldo insuficiente).

[ ] 5.4. Consultas avanzadas (Votos y SP):
    - [POST /peliculas/<id>/votar]: Votar una película (recibe puntuación 0-10).
      * INSERT / UPDATE en tabla valoraciones.
    - [GET /peliculas/<id>/valoracion]: Consultar puntuación media.
      * Debe invocar el Procedimiento Almacenado / Función creada en la BD (SELECT sp_calcular_valoracion_media(:id)).

[ ] 5.5. Endpoint clave para optimización:
    - [GET /ventas/<año>/<país>]:
      * Ejemplo: /ventas/2026/Francia
      * Devuelve el historial de compras del año dado para clientes de esa nacionalidad.
      * Consulta con JOIN entre usuarios, pedidos y pedido_items / peliculas en UN ÚNICO execute().
